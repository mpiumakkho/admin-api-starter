# ดูแลระบบหลังนำขึ้นใช้งานจริง

สำหรับคนที่นำระบบหลังบ้านนี้ขึ้นใช้งานจริงและดูแลต่อ วิธีรันและตัวแปรสภาพแวดล้อมที่ต้องตั้งอยู่ใน [README](../README.md) ส่วนเหตุผลของแต่ละเรื่องอยู่ใน [02-DECISIONS.md](02-DECISIONS.md)

## งานที่ระบบรันเองตามเวลา

เวลาในตารางเป็นเขตเวลาขององค์กรที่ตั้งใน `access-control.time-zone` (ตัวแปร `AC_TIME_ZONE` ค่าเริ่มต้น `Asia/Bangkok`) ไม่ใช่เขตเวลาของเครื่อง ซึ่งในคอนเทนเนอร์เป็น UTC (P-030)

| งาน | เมื่อไร | ทำอะไร | ถ้ารอบหนึ่งไม่ได้รัน |
| --- | --- | --- | --- |
| `InactiveAccountJob` (identity) | ทุกวัน 02:30 | ถ้าตั้ง `suspendInactiveDays` ไว้ (0 คือปิด และเป็นค่าเริ่มต้น) จะระงับบัญชีที่ไม่ได้ใช้นานกว่านั้น ยกเว้นผู้ดูแลสูงสุดคนสุดท้าย แล้วบันทึกประวัติและส่งอีเมลบอกเจ้าของบัญชี (P-027) | คืนถัดไปจะระงับเอง เพราะนับจากวันที่ใช้งานล่าสุด |
| `SessionCleanupJob` (authentication) | ทุกวัน 03:15 | ลบเซสชันที่ปิดหรือหมดอายุไปเกิน 30 วัน และลิงก์ในอีเมลที่หมดอายุเกิน 30 วัน | ไม่กระทบการใช้งาน แค่ข้อมูลเก่าค้างนานขึ้น |
| `AuditRetentionJob` (audit) | ทุกวัน 03:30 | ลบประวัติการใช้งานที่เก่ากว่า `activityRetentionDays` (อย่างน้อย 90 วัน: P-026) | ประวัติถูกเก็บนานกว่าที่ตั้งไว้หนึ่งวัน |
| `AccessReviewJob` (review) | ทุกชั่วโมง นาทีที่ 5 | ปิดรอบทบทวนสิทธิ์ที่ครบกำหนด แล้วถอดบทบาทที่ตัดสินว่าให้ถอด (P-028) | ปิดในชั่วโมงถัดไป |
| `RoleAssignmentExpiryJob` (identity) | ทุก 5 นาที เริ่มหลังระบบเปิด 1 นาที | บันทึกประวัติ `role_assignment.expired` ของการมอบบทบาทที่หมดเวลา และลบการมอบที่สิ้นสุดไปนานกว่าระยะเก็บประวัติ (P-019) | สิทธิ์หยุดมีผลตั้งแต่หมดเวลาอยู่แล้ว มีแค่ประวัติที่ลงช้า |
| `ChangeStreamService.ping` (liveupdate) | ทุก 25 วินาที | ส่งสัญญาณไปที่หน้าจอที่รอฟังการเปลี่ยนแปลง (SSE) เพื่อไม่ให้ proxy ตัดการเชื่อมต่อเพราะเงียบนาน | — |

`SessionCleanupJob` เขียน log ระดับ INFO ทุกคืน แม้จะไม่ได้ลบอะไร จึงใช้ดูได้ว่างานตามเวลายังรันอยู่ งานอื่นเขียน log เฉพาะเมื่อได้ทำอะไร เช่น `Suspended 3 accounts not used for 90 days` หรือ `Closed 1 access reviews on their due date`

## หลายอินสแตนซ์

ข้อมูลทั้งหมดอยู่ใน PostgreSQL จึงรันหลายอินสแตนซ์ได้ (เงื่อนไขดูใน [README](../README.md)) แต่งานตามเวลาไม่มีตัวกลางที่เลือกว่าใครเป็นคนรัน **ทุกอินสแตนซ์จึงรันทุกงานพร้อมกัน**

- **รันซ้ำได้ไม่มีผล:** `SessionCleanupJob` และ `AuditRetentionJob` เพราะอินสแตนซ์ที่ลบทีหลังจะไม่เจออะไรให้ลบแล้ว
- **กันการทำซ้ำไว้แล้ว:** `AccessReviewJob` ล็อกรอบทบทวนก่อนปิด (`for update`) และข้ามรอบที่ปิดไปแล้ว ส่วน `RoleAssignmentExpiryJob` ทำเครื่องหมายแบบมีเงื่อนไขก่อนบันทึกประวัติ อินสแตนซ์ที่ทำเครื่องหมายไม่สำเร็จจะข้ามไป
- **ยังทำซ้ำ: `InactiveAccountJob`** ทุกอินสแตนซ์อ่านรายชื่อชุดเดียวกันโดยไม่ล็อก แล้วระงับคนเดียวกันทั้งหมด ประวัติการระงับจึงซ้ำ และเจ้าของบัญชีได้อีเมลซ้ำเท่าจำนวนอินสแตนซ์ นอกจากนี้ ถ้ามีผู้ดูแลสูงสุดที่ไม่ได้ใช้งานหลายคน แต่ละอินสแตนซ์จะนับ "ผู้ดูแลคนสุดท้าย" โดยไม่เห็นกัน ระหว่างที่ยังไม่ได้แก้ ถ้ารันหลายอินสแตนซ์ให้ปิดการระงับอัตโนมัติ (ตั้ง `suspendInactiveDays` เป็น 0) หรือยอมรับว่าประวัติและอีเมลจะซ้ำ
- `ChangeStreamService.ping` แต่ละอินสแตนซ์ส่งให้เฉพาะหน้าจอที่ต่ออยู่กับตัวเอง

## คีย์

### คีย์เซ็นโทเค็น (`AC_JWT_*`)

สร้างด้วย `tools/gen-keys.sh` แล้วตั้งเป็นตัวแปรสภาพแวดล้อม ระบบเซ็นโทเค็นด้วยคีย์คู่สุดท้ายใน `access-control.token.keys` และตรวจกับทุกคู่ ส่วนคุกกี้ต่ออายุการเข้าสู่ระบบเป็นค่าสุ่มที่เก็บในฐานข้อมูล ไม่ได้เซ็นด้วยคีย์นี้

- **อินสแตนซ์เดียว:** ใส่คีย์คู่ใหม่แทนคู่เดิมแล้วนำขึ้นใหม่ โทเค็นเดิมจะใช้ไม่ได้ทันที แต่แอปจะได้ 401 แล้วใช้คุกกี้ขอโทเค็นใหม่ให้เองครั้งเดียว ไม่มีใครต้องเข้าสู่ระบบใหม่
- **หลายอินสแตนซ์ที่นำขึ้นทีละตัว:** ต้องทำสามรอบ ไม่อย่างนั้นระหว่างที่กำลังนำขึ้น โทเค็นจากอินสแตนซ์หนึ่งจะใช้กับอีกอินสแตนซ์ไม่ได้
  1. ตั้งเป็น `[ใหม่, เก่า]` ระบบยังเซ็นด้วยคู่เก่า แต่ทุกอินสแตนซ์ตรวจคู่ใหม่ได้แล้ว
  2. ตั้งเป็น `[เก่า, ใหม่]` ระบบเริ่มเซ็นด้วยคู่ใหม่
  3. รออย่างน้อย 15 นาที (อายุของโทเค็น) แล้วตั้งให้เหลือแค่ `[ใหม่]`

  ตอนนี้ `application-prod.yml` รับคีย์จากตัวแปรสภาพแวดล้อมได้คู่เดียว ช่วงเปลี่ยนคีย์จึงต้องเพิ่มคู่ที่สองในไฟล์ตั้งค่าเอง

### คีย์เข้ารหัสข้อมูลลับในฐานข้อมูล (`AC_ENCRYPTION_*`)

สร้างครั้งเดียวด้วย `tools/gen-keys.sh` แล้วเก็บไว้ตลอด **ห้ามเปลี่ยน** เพราะถ้าเปลี่ยน ข้อมูลลับของการยืนยันตัวตนสองขั้นตอนที่เก็บไว้จะถอดรหัสไม่ได้ (P-014) และยังไม่มีวิธีเข้ารหัสใหม่ด้วยคีย์ใหม่ ถ้าไม่ได้ตั้งไว้ ระบบจะไม่ยอมเริ่มทำงาน

## สำรองและกู้คืนข้อมูล

- ทุกอย่างที่ต้องเก็บอยู่ใน PostgreSQL ฐานเดียว คือสคีมา `access_control` (ผู้ใช้, บทบาท, การมอบบทบาท, สาขา, เซสชันและโทเค็นต่ออายุที่เก็บเป็นค่า hash, ประวัติการใช้งาน, การตั้งค่า, รอบทบทวนสิทธิ์ และ `flyway_schema_history`) กับสคีมา `app` ของงานเฉพาะโปรเจกต์
- อินสแตนซ์ไม่เก็บอะไรลงดิสก์ อีเมลส่งออกไปทันที ส่วนการเชื่อมต่อของหน้าจอกับแคชอยู่ในหน่วยความจำ จึงทิ้งอินสแตนซ์แล้วสร้างใหม่ได้เสมอ
- เก็บ `AC_ENCRYPTION_PASSWORD` และ `AC_ENCRYPTION_SALT` ไว้คู่กับข้อมูลสำรอง ถ้าไม่มี ข้อมูลลับของการยืนยันตัวตนสองขั้นตอนในข้อมูลสำรองจะใช้ไม่ได้ ส่วนคีย์เซ็นโทเค็นสร้างใหม่ได้
- ประวัติการใช้งานเป็นหลักฐานสำหรับผู้ตรวจสอบ (P-026) การกู้คืนจากข้อมูลสำรองรายวันจะทำให้ประวัติหลังเวลาที่สำรองหายไป ถ้าต้องไม่หาย ให้ใช้การกู้คืนถึงจุดเวลาใดก็ได้ของ PostgreSQL (point-in-time recovery ด้วย WAL archiving)
- หลังกู้คืน เซสชันจะย้อนกลับไปเป็นตามเวลาที่สำรอง คนที่คุกกี้ถูกเปลี่ยนใหม่หลังจากนั้นจะต้องเข้าสู่ระบบใหม่

## นำรุ่นใหม่ขึ้นใช้งาน

- Flyway ปรับโครงสร้างฐานข้อมูลตอนระบบเริ่มทำงาน ก่อนรับคำขอแรก หลายอินสแตนซ์เริ่มพร้อมกันได้ เพราะ Flyway ล็อกให้ปรับได้ทีละตัว
- การปรับโครงสร้างฐานข้อมูลเดินหน้าอย่างเดียว ถ้าอาจต้องถอยกลับไปรุ่นก่อนที่โครงสร้างต่างกัน ให้สำรองข้อมูลก่อนนำขึ้น
- ระหว่างนำขึ้นทีละอินสแตนซ์ รุ่นเก่ากับรุ่นใหม่ใช้ฐานข้อมูลเดียวกัน ถ้ารุ่นใหม่ลบหรือเปลี่ยนชื่อคอลัมน์ (เช่น `V4__role_assignments.sql` ที่เอา `users.role_id` ออก) ให้หยุดทุกอินสแตนซ์ก่อนนำขึ้น

## ตรวจสถานะระบบ

- `GET /actuator/health` เรียกได้โดยไม่ต้องเข้าสู่ระบบ (เป็นทางเดียวของ actuator ที่เปิดไว้) ตอบ `{"status":"UP"}` หรือ `DOWN` (503) โดยไม่บอกรายละเอียด
- จะเป็น `DOWN` เมื่อต่อ PostgreSQL **หรือเซิร์ฟเวอร์อีเมล (SMTP)** ไม่ได้ เพราะ Spring Boot ตรวจเซิร์ฟเวอร์อีเมลด้วย ใช้เฝ้าระวังและแจ้งเตือนได้ แต่อย่าใช้เป็นตัวตัดสินว่าระบบค้าง (liveness probe) ไม่อย่างนั้นแค่เซิร์ฟเวอร์อีเมลล่ม ระบบจัดการคอนเทนเนอร์ก็จะสั่งรีสตาร์ททุกอินสแตนซ์
- บน Kubernetes Spring Boot เปิด `/actuator/health/liveness` และ `/actuator/health/readiness` ไว้ให้ใช้เป็นตัวตรวจสถานะ บนระบบอื่นให้ตั้ง `management.endpoint.health.probes.enabled=true`

## log ที่ควรเฝ้า

log ของระบบจริงเป็น JSON รูปแบบ ECS (`application-prod.yml`) ทุกบรรทัดที่เกิดระหว่างคำขอมี `request_id` ซึ่งตรงกับ `requestId` ในข้อผิดพลาดที่ตอบกลับไป

| ข้อความใน log | ระดับ | ความหมาย | ต้องทำอะไร |
| --- | --- | --- | --- |
| `Could not send "…" to …` | ERROR | ส่งอีเมลไม่ได้ และระบบไม่ส่งใหม่ | ตรวจเซิร์ฟเวอร์อีเมล คนที่รอลิงก์ขอใหม่ได้ (ส่งคำเชิญซ้ำ หรือขอรีเซ็ตรหัสผ่านอีกครั้ง) ส่วนอีเมลแจ้งเตือนที่ส่งไม่ได้จะหายไป |
| `Request failed` | ERROR | ข้อผิดพลาดที่ไม่ได้ตั้งใจ (500) | ใช้ `request_id` หาบรรทัดอื่นของคำขอเดียวกัน |
| `A replaced refresh token was used again; ending session …` | WARN | คุกกี้ต่ออายุที่ถูกเปลี่ยนไปแล้วถูกใช้ซ้ำเกิน 30 วินาที ระบบถือว่าถูกขโมยและปิดเซสชันนั้น | ถ้าเกิดกับคนเดียวซ้ำ ๆ อาจถูกขโมยคุกกี้จริง ถ้าเกิดกับหลายคน ให้ตรวจ proxy หรือโปรแกรมที่ส่งคำขอซ้ำ |
| `Lost the connection that hears about changes; connecting again in …` | WARN | อินสแตนซ์หลุดจากการฟังการเปลี่ยนแปลง (`LISTEN`) ระหว่างนั้นหน้าจอที่ต่อกับอินสแตนซ์นี้จะไม่รู้ว่ามีการเปลี่ยนแปลงจากอินสแตนซ์อื่น | ถ้าไม่หายเอง ให้ตรวจการเชื่อมต่อฐานข้อมูล |
| `No access-control.token.keys configured: …` | WARN | ไม่มีคีย์เซ็นโทเค็น ทุกครั้งที่รีสตาร์ท ทุกคนต้องขอโทเค็นใหม่ | ระบบจริงต้องไม่มีบรรทัดนี้ ให้ตั้ง `AC_JWT_*` |
| `There are no users yet: set access-control.bootstrap.admin-password …` | ERROR (start ไม่สำเร็จ) | ฐานข้อมูลยังไม่มีผู้ใช้และไม่ได้ตั้งรหัสผ่านของผู้ดูแลคนแรก หรือตั้งสั้นกว่ากฎรหัสผ่าน | ตั้ง `ACCESS_CONTROL_BOOTSTRAP_ADMIN_PASSWORD` (อย่างน้อย 8 ตัว) แล้ว start ใหม่ ใช้เฉพาะตอนที่ยังไม่มีผู้ใช้ ระบบไม่เขียนรหัสนี้ลง log |
